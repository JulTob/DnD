## 🔍 Diagnosis (what & where)
We need a TOP model where each Character’s known spells are private to that Agent — Charlie’s list must not collide with Alice’s, and querying “known” must not merge Fields across beings. A sketch proposed `char.CharTag` so `KnownSpells(char.CharTag)` would mint Tags that “only live on” that Character (a per-instance namespace).

## 🧾 Evidence
Doctrine already names “Known spells via a `Known(spell)`-style tagging / Field query” as an Operation/Field example. Guide: Records are Agent state (fresh per Agent); Reports are shared Tag/Field data. TagKit materializes Records onto the Agent instance (`__setattr__`), not onto a shared Tag store. `Character_Tag` already exists as the *root for Tags a Character may bear* (target Pre) — that is not a per-instance namespace Tag.

## 🎯 Desired outcome
A decreed pattern for “this Character knows these Spells” that:
1. isolates state per Character,
2. stays idiomatic TagKit (no invented parallel namespace layer),
3. composes with SpellsKit / QST-0031,
4. supports sheet/query without cross-Character leakage.

## 🧭 Notes for the Agora / implementer
**Open a Dialog** before coding. Options to weigh (problem statement only — decide in Agora):
- **A. Record on the Character** — e.g. Spellcaster Tag contributes a fresh `known_spells` Record per Agent; Field = who casts, not which spells.
- **B. Relational tagging** — Spells as Agents in a Character-scoped relation (needs a clear TagKit-shaped mechanism; may be `tagkit-upstream` if blocked).
- **C. Per-instance CharTag / Tag factory** — Julio’s sketch; only if A/B cannot express Field queries cleanly without inventing outside the Guide.

Do not treat mutable shared defaults or Tag-level Reports as “per Character.” Crash fears from two Agents both bearing the same Tag class are usually a modeling mistake, not a TagKit Field bug.

## 🏛️ Council
> Wizard Consul: Two Characters in `Spellcaster` is the design — the Field is the population of casters. Their Records must be fresh lists; a shared list would be a Report (or a bug).
> Warlock Consul: `Known(spell)` as one global Field mixes every caster’s book. That is the real collision. Fix the relation model, don’t mint a CharTag per life unless TagKit forces it.
> Monk Consul: Prefer A until a query needs Field iteration over spells-known-by-X. YAGNI on namespaces.
> Druid Consul: Keep `Character_Tag` as target-root; don’t overload it into per-instance isolation.
> Lorekeeper Consul: If B needs TagKit support we lack, mint `tagkit-upstream` — don’t fork a local namespace protocol.
