## 🔍 Diagnosis (what & where)

`AtlasActorLudi/SpeciesKit/Aasimar/Map_of_Ideals.py` calls `_opening(...)` at **three** sites and defines it at none:

```
228:  f"{_opening(self.descent)} of {held} stands somewhere behind you.",
250:  f"{_opening(shade)} talaria sit at {place}, and anyone who notices "
268:  f"{_opening(form)} hangs over you in {self.colour}. {self.tell}",
```

`grep -n "_opening"` returns those three uses and nothing else. The helper was lost when the file was restored; the call sites survived. The file itself is **real authored source** (407 lines of Julio's prose), not a bytecode bootstrap, so only this one helper is missing.

From its three uses, `_opening` takes a noun phrase and returns it as an opening clause with the right indefinite article and capitalisation ("A choir…", "An aureole…"). That is an inference from the call sites, **not** a specification.

## ✅ Resolution
- **Decided by:** Claude, 2026-08-30 (no decision needed — the bytecode settled it)
- **What changed:** `_opening` restored to `AtlasActorLudi/SpeciesKit/Aasimar/Map_of_Ideals.py`, verbatim from the vault code object:
  ```python
  def _opening(phrase):
      """A phrase promoted to the start of a sentence, capital and all."""
      return phrase[:1].upper() + phrase[1:]
  ```
  Its docstring came back with it. `NameError: name '_opening' is not defined` no longer appears anywhere in a 180-Character sweep; the failure causes went from three to two.
- **Practice/preference to remember:** **the diagnosis in this ticket guessed wrong, and recovering rather than rewriting is what saved it.** Reading only the three call sites (`f"{_opening(self.descent)} of {held} stands…"`) suggested an *indefinite-article* helper returning "A choir" / "An aureole". It is nothing of the kind — it is a capitalisation helper. An agent that had written the plausible version would have produced code that passed every test while quietly changing the prose, and nothing downstream would ever have flagged it.

  Two general lessons for the rest of the recovery:
  1. **No decompiler supports Python 3.14** (`decompyle3` refuses outright), but that does not mean the bytecode is opaque. String constants come back **verbatim** — 46 authored strings survive in this one module — and a small function is fully determined by its disassembly. Reconstruction is hand work guided by `dis`, not guesswork.
  2. Where the lost code is **authored voice**, treat a plausible reconstruction as a wrong answer, not a partial one.
